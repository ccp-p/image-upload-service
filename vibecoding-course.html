先翻译：Vibe Coding 到底是什么

英文 vibe 听起来像气氛，但在工程里它不能只靠气氛。

需求引入

你今天要解决的问题是：AI 写出来的代码有时像“碰运气”。我们把这运气换成一套可以被检查的流程。

翻译：Vibe Coding 代表一种协作方式，你负责给出上下文、约束和验收标准，AI 负责生成实现；如果结果不合格，就修正约束，而不是只换一句咒语。

最小流程

整套课程只有一个主循环，后面六课只是把它拆开练。你的重点不是亲手写每个文件，而是设计提问、验收输出、迭代约束。

工程循环
1. 给上下文

AI 知道项目是什么，不是靠猜。

2. 写约束

AI 知道做什么，更要知道不做什么。

3. 定验收

AI 知道“对”的定义，不是只求能跑。

4. 生成实现

这里才轮到 AI 发挥。

5. 审查

检查安全、边界、并发和一致性。

6. 记忆

把纠错结果固化，避免下次失忆。

AI 代跑心法：不要把 AI 当成“帮我省掉思考的按钮”。它负责草稿、查资料和批量修改；你负责提出需求、追问不清楚的地方、检查风险、决定接受还是退回。
总控代跑提示词
你是我的 Vibe Coding 教练。请带我完成 L1 到 L6，不要一次性给我所有内容。

每一课按这个流程走：
1. 先问我这一课对应的小需求；
2. 让我确认或补齐上下文；
3. 你生成草稿文件或提示词；
4. 让我审查并指出哪些地方是编造或不符合项目；
5. 你根据反馈修正；
6. 只在验收通过后才进入下一课。

输出要求：
1. 每次只处理当前这一课；
2. 每课都给我一个可复制的提示词或文件草稿；
3. 每课最后给一个验证步骤；
4. 如果我还没确认，不要跳到下一课。

课程列表：
L1 AGENTS.md 入职手册；
L2 可执行 Spec；
L3 测试先行；
L4 Review Checklist；
L5 任务拆分；
L6 项目记忆系统。

学习节奏

每课大约 25 分钟。卡住不是失败，是提示你要把某个约束写得更清楚。

  • 先试错，别直接看答案。
  • 每课只做一个真实小任务。
  • AI 生成后自己跑一遍，再把错误交回给它修。
  • 到这里有问题吗？把问题写在每课笔记里，不要跳过。
锚点：AI 不是替你决定“对”的人，它是在你的定义里寻找“怎么做”的人。
L1

给 AI 写一份入职手册

目标：把“项目里隐含的常识”变成 AGENTS.md。

需求引入

假设你招了一个很强的实习生，但他说：“帮我把收藏功能做了。”你会先给他项目地图，而不是直接让他盲改代码。

翻译：AGENTS.md 代表一份项目入职手册，它告诉 AI 技术栈、目录规则、编码约定和绝对不能踩的坑。

先来试错

下面是最裸的请求。你先猜：AI 会从哪里开始猜？然后逐个点亮上下文，看风险怎么下降。

上下文补给器
帮我在这个项目里加一个用户收藏功能。
试错提醒：没有目录结构时，AI 可能把 Go CLI 的 main.go 放错位置；没有测试规则时，它可能给你引入新框架；没有禁止事项时，它可能顺手做一个你不想要的 UI。

叠加一层：让 AI 帮你起草 AGENTS.md

先不要自己写模板。把下面的提示词交给 AI，让它读取当前仓库并生成草稿。你只需要审核、删掉编造内容、补上禁止事项。

AI 代跑提示词
你是我的项目协作者。请先读取当前仓库，帮我生成一份 AGENTS.md 草稿。

要求：
1. 只根据仓库里真实存在的文件、依赖、脚本和目录结构来写，不要编造。
2. 包含：项目概述、技术栈、目录结构、编码规范、绝对不要做的事。
3. “绝对不要做的事”至少写 5 条，重点覆盖依赖、状态文件、测试、部署和 Windows 兼容。
4. 如果有不确定的事实，先列出最多 5 个问题等我回答，不要猜。
5. 最后给我一个 5 行以内的验证清单，告诉我怎么检查草稿是否贴合项目。
AI 草稿粘贴区

验证

用同一个请求在新对话里测两次：一次没有手册，一次有手册。差异就是你今天创造的工程价值。

锚点：入职手册的核心不是面面俱到，而是把 AI 最容易猜错的地方提前钉住。
L2

写出 AI 能执行的任务描述

目标：把模糊需求翻译成 Spec。

需求引入

“帮我写个接口”缺了太多变量：什么路由？什么输入？什么输出？哪些不做？AI 只能编。

翻译：Spec 代表一份可执行任务合同，它说明输入、输出、业务规则、明确不做的事和依赖。

先来试错

你觉得“写一个 API 接口”至少缺几个信息？数完再看：路由、鉴权、分页、字段名、错误码、边界、返回格式、测试标准——常常八个都缺。

修正理解：AI 不是读心者。Spec 的目标不是写成法律文书，而是消除会导致返工的歧义。

动手：让 AI 先问，再生成 Spec

先给它一个粗糙需求，让它反过来问你。等它问清楚了，再让它按模板产出 Spec。

Spec 代跑提示词
我想做一个小功能：[用一句话写粗糙需求]。

请先不要生成代码，也不要直接给完整 Spec。
第一步，像需求评审一样问我最多 5 个关键问题，覆盖：
1. 谁会使用它，入口在哪里；
2. 输入参数和边界值；
3. 成功输出和失败输出；
4. 权限、数据来源和依赖；
5. 明确不需要做的事。

等我回答后，再按下面的模板生成 Spec：
## 任务
### 输入
### 输出
### 业务规则
### 不需要做的事
### 依赖

要求：
1. 业务规则至少 3 条。
2. “不需要做的事”至少 2 条。
3. 不要引入未确认的技术方案。
4. 如果仍有关键歧义，先继续问，不要猜。
Spec 审核器
有标题
输入明确
输出明确
规则至少 3 条
不做的事至少 2 条
依赖说明

迭代逼近

第一轮不用追求完美。真实流程是：生成 → 你发现漏了错误处理 → 补 Spec → 再生成 → 发现边界不对 → 再补。

  • 第一轮：让它跑通主路径。
  • 第二轮：补错误码和空值。
  • 第三轮：补并发、权限、分页、时间格式。
锚点：“不需要做的事”和“需要做的事”同样重要。
L3

先写测试，再让 AI 写代码

目标：把“我觉得对”变成机器能验证的定义。

需求引入

现在需要一个 isValidEmail(email)。可以让 AI 先生成测试，但你要审核测试是不是覆盖了业务边界，然后再让它写实现。

翻译：测试代表一条可自动执行的验收标准，它告诉你定义里的“对”到底是什么。

试错实验室

下面的默认正则看起来很聪明，但会让某个非法邮箱通过。先点运行，再看失败行。

输入期望实际结果
 
点击“运行测试”。
修正理解：默认正则让 test @gmail.com 通过，因为 . 允许空格。更稳的一版是 /^[^\s@]+@[^\s@]+\.[^\s@]+$/，但最终规则必须由你的业务决定。

两步代跑：先生成测试，再写实现

不要只说“写个邮箱验证”。让它先产出测试，再实现。这样可以避免它一边写规则一边挑好过的用例。

第一步：生成测试
我要实现一个 isValidEmail(email) 函数。

请先生成 5-8 个测试用例，不要写实现。
用例必须覆盖：
1. 标准邮箱；
2. 带 + 号的邮箱；
3. 没有 @；
4. @ 前为空；
5. 有空格；
6. 你认为有争议的边界，比如 a@b.c。

输出格式：
输入 / 期望值 / 为什么。
不要引入测试框架，不要修改项目文件。
第二步：按测试实现
我已经写好了测试用例：
1. test@gmail.com 期望 true
2. test+tag@gmail.com 期望 true
3. testgmail.com 期望 false
4. @gmail.com 期望 false
5. test@ 期望 false
6. test @gmail.com 期望 false
7. a@b.c 期望 true

请只实现 isValidEmail(email)，不要引入第三方依赖，
不要修改测试，让全部用例通过。
锚点：你定义“什么是对的”，AI 负责“怎么做到”。
L4

建立你的 Review Checklist

目标：从“看起来能跑”升级到“敢上线”。

需求引入

AI 写出一个“创建订单”接口后，可以让它先按清单自查；你要抽查高风险项，而不是逐行手写注释。

翻译：Review Checklist 代表一份上线前风险地图，它防止你每次只凭直觉扫一眼。

审查闯关

下面六张卡都是 AI 常见翻车点。先自己猜问题，再点开。

输入校验price = req.body.price
价格可能是负数、字符串、NaN 或极大值。必须先校验类型和范围。
权限updateUser(params.userId)
不能只信 URL 参数。应从登录态取当前用户，再检查角色。
并发stock--
同一秒两次下单可能超卖。要用原子更新、锁或唯一约束。
事务saveInventory(); saveOrder();
第二步失败时，第一步已经生效。两者要放进同一个事务。
敏感字段return user
返回整个用户对象可能带出 passwordHash、token 或内部字段。
错误暴露catch(err){ res.send(err.stack) }
堆栈可能暴露路径、SQL 和依赖版本。对外要换成安全错误码。
已发现 0 / 6 个风险点。

AI 代跑 Review

让 AI 先自查，再由你抽查。它不能替代你决定业务风险。

锚点：“能跑”只是起点，并发、权限和事务才是上线分水岭。
L5

把大象装进冰箱：任务拆分

目标：一次只给 AI 一个可验证的 PR。

需求引入

“实现一个完整文章系统”不是任务，是项目。可以让 AI 拆任务，但拆分结果必须由你确认依赖顺序和验收标准。

翻译：任务拆分代表把大目标切成有依赖顺序的小交付，每个小交付都能单独测试和 Review。

让 AI 拆，你来验收

先把大需求交给 AI 拆分。确认没有循环依赖、每个 PR 都能独立测试后，再进入模拟器。

拆分代跑提示词
我有一个中等复杂度需求：实现一个文章发布系统，包括富文本编辑、草稿自动保存、定时发布、标签分类、文章审核流程、SEO 元数据生成。

请先不要写代码，帮我做任务拆分。

输出：
1. 按依赖顺序列出子任务；
2. 每个子任务给一个独立 PR 名；
3. 标明前置依赖；
4. 每项写清楚输入、输出、业务规则和至少一条测试；
5. 每项写“不需要做的事”；
6. 标出哪些任务可以并行。

约束：
1. 每个 PR 控制在一次可以审查的规模；
2. 不允许循环依赖；
3. 每一步都要能独立验证；
4. 不要一次给我所有代码。
依赖解锁模拟器

一个 PR 的执行合同

每个 PR 都走一遍 L2-L4，不要把八个功能混在同一个 prompt 里。

任务：实现文章-标签关联
前置：标签 CRUD 已完成；文章基础 CRUD 已完成。

输入：
- POST /api/articles/:id/tags
- body: { "tagIds": [1,2] }

输出：
- 成功：{ "code": 0, "data": { "articleId": 1, "tagIds": [1,2] } }
- 失败：404 文章不存在；400 标签不存在或重复。

业务规则：
1. 只允许文章作者修改关联。
2. tagIds 去重后最多 10 个。
3. 关联操作放在事务里。

不需要做：
- 不做标签管理页面。
- 不做文章搜索。

验收：
- 先写测试，再实现；测试必须覆盖空数组、重复标签、无权限、文章不存在。
锚点：一次改一件事，一次验一件事。
L6

项目记忆系统

目标：让纠错结果活到下一个新对话。

需求引入

你上周说过“不要用 moment.js”，这周新对话里 AI 又用了。问题不是它笨，是项目没有记忆。这一步也可以让 AI 从对话和代码里提炼记忆。

翻译：项目记忆代表一组持久文件，包括规则、常见模式和错误日志，让 AI 每次进入项目都带着同样的约束。

三个文件，一个闭环

AGENTS.md

放项目事实、目录和硬约束。

docs/PATTERNS.md

放“新建接口/页面”的标准流程。

docs/ERRORS.md

放踩过的坑、正确做法和修复方案。

让 AI 帮你提炼记忆

把“AI 又错了”翻译成可复用规则。可以让 AI 读最近的对话或 diff，提炼坑和正确做法，最后由你确认放哪里。

记忆提炼提示词
请读取我提供的最近对话、代码 diff 或错误记录，帮我提炼项目记忆。

输出格式：
## 日期：[日期]
- 坑的标题：
- 问题：AI 做错了什么；
- 正确：项目里应该怎么做；
- 放入：AGENTS.md / docs/PATTERNS.md / REVIEW_CHECKLIST.md；
- 验证：下次怎么检查它是否生效。

要求：
1. 不要泛泛地说“注意安全”，必须给可执行规则；
2. 每条记录都写成下次 AI 能遵守的约束；
3. 如果某条更适合放 Review Checklist，请说明原因；
4. 不要编造我没提供的事实。
坑记录转换器

最终验证

开一个全新对话，让 AI 做以前犯过错的同一件事。如果它不再犯，记忆系统开始工作了。

锚点：每次纠错都应该问一句：这要不要变成规则、模式或检查表？
本地保存，不联网提交。 从 L1 开始，不要跳课。
